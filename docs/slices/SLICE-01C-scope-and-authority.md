## 1 Outcome

The department boundary is decided by the server on every discovery read rather
than by the browser over a seed, the authority check evaluates its department
gate one row at a time, and the authority table carries the line-of-defence
constraint the customer can later turn on.

---

## 2 Functional purpose

A user comes to a register to find the work that is theirs. FRD §4.5 states the
rule that decides what they see, and states it as a derivation rather than a
permissions tree: a record takes its department from whoever owns it, so the
boundary follows the org chart without a second structure to keep in step with
it. A person sees the records owned by people in their own department. Compliance
and Company Secretarial keeps the cross-department view, because holding the
whole obligation picture is that function's job. The Administrator sees
everything, because configuring the platform requires it.

The boundary applies where work is discovered, which is lists, registers,
calendars and the personal queue. It deliberately does not apply to navigation: a
detail page stays reachable by direct link and by command search, so a
cross-reference never dead-ends and a person handed a record identifier can
always open it. FRD §4.5 calls that a deliberate design choice and asks for it to
be preserved. `platform.md` section 3 carries the same two rules over every read.

None of it is enforced today. `apps/web/src/lib/access.ts` computes the boundary
in the browser, over the seed, from the role the switcher last selected. The
server was checked on 2026-08-30 and no read anywhere in `apps/api/src` reads the
caller's department: `GET /controls` and `GET /instruments` return every row
regardless of who asks. SIM-NAV-002 in the screen inventory records this, and
FLR-03 records the same gap on the floor. A boundary a determined user can defeat
by reading the response is not a boundary, and FRD G-03 requires the client check
to become an affordance rather than the control.

The second half of the slice is the authority check itself. D-046 settles DN-023:
the department gate evaluates per row, so a caller is permitted when at least one
row is satisfied completely. Today `AuthorityService.assert` asks whether every
permitted row names a department before testing the caller's, which was correct
while every action's rows were uniform. D-037 made `instrument.create` the first
action where they are not, and under the old reading the Administrator row would
switch the department test off for the Compliance Manager row beside it. Priya
Sharma, the Data Protection Officer, would then be able to register a source act
that `BR-AUT-02` exists to keep from her. D-047 adds the line-of-defence column
from `BR-AUT-10`, empty for every action in the first release, so the shape is in
the table before the table carries real configuration.
