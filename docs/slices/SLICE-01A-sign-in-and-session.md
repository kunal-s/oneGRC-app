## 1 Outcome

A person arrives at the build, is identified by the customer's own identity
system rather than by choosing a name from a list, holds a server-side session
that expires and can be revoked, and the platform stores no credential of any
kind.

---

## 2 Functional purpose

A user comes to this surface to establish who they are, once, so that every
screen after it can answer a different question: what may this person see, and
what may they do. FRD §4.3 makes the distinction load-bearing. A person is
accountable, escalation resolves to a person, and the audit trail names a person.
Everything downstream of identity is worthless if identity is a guess.

Today it is a guess. FRD §19 G-02 records the prototype's position plainly: the
persona switcher is the only authentication, and one reviewer plays six people.
FRD §23 D-12 names the same thing as the demo's most consequential shortcut. The
development identity bar already made half the correction, moving the choice from
the browser to the server through `POST /api/dev/impersonate`, which is why
SCR-096 reads as `wired` in the screen inventory while SCR-082 reads as
`scaffolded`. What it did not do is make the choice real: any visitor may still
become the Head of Compliance by picking her from a list.

D-044 settles how that closes. Sign-in federates to the customer's existing
identity system and the platform holds no credentials at all: no password, no
reset path, no lockout, no second factor of its own. The platform's `Person`
already carries no credential field, so this is the shape the schema was built
for. What the slice adds is the exchange that turns an assertion from the
customer's identity provider into one of the platform's own sessions, and the
refusal that applies when the identity provider names somebody the platform has
never heard of. Rule 7 governs that refusal: nothing is tracked without a person,
and a person is created by an administrator, never by the act of arriving.

FRD §17.4 and the floor entry FLR-02 are what this slice moves. FLR-02 reads
"Server-side sessions exist, minted by a development impersonation endpoint.
There is no real sign-in." At the end of this slice it reads real.

| Line | Fact |
|---|---|
| GAP-SCR-011-001 | The platform renders no username field, no password field and no credential form of any kind, on any route. D-044 |
| GAP-SCR-011-002 | An unauthenticated request to any application route sends the browser to the customer's identity provider. FRD G-02, D-044 |
| GAP-SCR-011-003 | The identity provider returns to one callback route, which exchanges the assertion for a platform session and then sends the browser to the route originally requested |
| GAP-SCR-011-004 | The route originally requested is preserved across the round trip, so a person following a deep link to a record arrives at that record and not at the home screen. FRD §4.5, which requires a person handed a record identifier to be able to open it |
| GAP-SCR-011-010 | The session is stored server side as E-08 `Session`, carrying `personId`, `createdAt`, `expiresAt` and `revokedAt`. The row already exists at `apps/api/prisma/schema.prisma:716` and gains no columns in this slice |
| GAP-SCR-011-011 | The session reaches the browser as one cookie, `httpOnly`, `sameSite` lax, `path` `/`, and `secure` when running in production. This is the pattern already set at `apps/api/src/core/identity/identity.controller.ts:48` and it does not change |
| GAP-SCR-011-012 | The client never asserts identity. `GET /whoami` is the only source of who is acting, and it reads the session, never a request body or header the browser controls. `platform.md` section 1, FRD `BR-AUT-01` |
| GAP-SCR-011-013 | A session past its `expiresAt` is not accepted. The next request sends the browser to the identity provider, per GAP-SCR-011-002 |
| GAP-SCR-011-014 | Signing out sets `revokedAt` on the session and clears the cookie. A revoked session is not accepted again |
| GAP-SCR-011-020 | The identity provider asserts a subject the platform holds no `Person` for: the person is refused and no `Person` record is created. Rule 7, nothing is tracked without a person |
| GAP-SCR-011-021 | The refusal at GAP-SCR-011-020 reads `You are signed in, but this platform has no record for you. Ask your administrator to add you.` and offers sign out as its only control. It does not reveal whether the subject exists under another address |
| GAP-SCR-011-022 | A `Person` whose `status` is not `Active` is refused on the same terms as GAP-SCR-011-020. E-03 carries `status PersonStatus`, `apps/api/prisma/schema.prisma:84` |
| GAP-SCR-011-030 | The identity provider cannot be reached: an error state states that sign-in is unavailable and does not fall back to any local sign-in path. There is no local path to fall back to, per GAP-SCR-011-001 |
| GAP-SCR-011-040 | The first administrator on a production install is created by an install-time step that is not gated behind an existing session. DN-029, and the mechanism is the subject of a decision needed, see section 8 |
| GAP-SCR-011-090 | Visual treatment: `NOT SPECIFIED`. The prototype has no sign-in surface, so D-042 gives the prototype nothing to rule on here. The redirect at GAP-SCR-011-002 renders nothing at all, which needs no design. The two states that do render, GAP-SCR-011-021 and GAP-SCR-011-030, reuse the prototype's `card-surface` and `Button` and carry no new visual vocabulary. **Transitions.** None. This slice performs no governed mutation on a domain
record. Sign-in and sign-out are platform events, logged under AUD-04 with the
person as actor.

**Permissions.** No new row in `ActionAuthority`. Signing in is not a governed
action: it is the thing that establishes who the caller is before any governed
action can be checked.

**Audit.** Two new entry kinds, both AUD-04: a session opened, and a session
ended, each naming the person and the time, and neither carrying any credential
or assertion content.

## 7 Verification

Performed by a non-developer, clicking, against both running apps. No step
requires reading code.

1. Open the prototype and the build side by side. Confirm the prototype has no sign-in surface at all, and that this is the gap the slice closes.
2. In the build, sign out. Confirm the browser goes to the customer's identity provider and that no username or password field belonging to the platform is ever shown.
3. Sign in as Anjali through the provider. Confirm you land on the home screen and the bottom bar shows her name, her department and her roles.
4. Sign out, then open a deep link to a record directly, for example an instrument detail address. Sign in when the provider asks. Confirm you arrive at that record and not at the home screen.
5. Use a provider account with no matching `Person`. Sign in. Confirm the refusal reads `You are signed in, but this platform has no record for you. Ask your administrator to add you.` and that the only control offered is sign out.
6. Confirm, by asking the administrator to look, that step 5 created no `Person` record.
7. Sign in, then have the administrator set your person's status to something other than Active. Reload. Confirm you are refused on the same terms as step 5.
8. Sign in, then wait past the session lifetime, or have the administrator revoke the session. Reload. Confirm you go back to the provider rather than seeing a blank screen or a stale identity.
9. Stop the identity provider, or point the configuration at an address that does not answer. Reload. Confirm the error state states that sign-in is unavailable and offers no local sign-in path.
10. In the development build only: confirm the bottom bar is present, reads `Dev identity`, and lists exactly the seven people at SCR-096-022 in that order, with those labels.
11. In a production build: confirm the bottom bar is absent from the page entirely, not merely disabled.
12. Compare the bottom bar against the prototype build side by side: same position, same border, same fill, same type size, same label text, same separator character.
13. Ask the administrator to show you the audit log for the last hour. Confirm your sign-in and your sign-out each appear, naming you and the time, and that neither entry contains a token, an assertion or a credential.
14. Run the verification commands. All pass.
15. Run the UI drift check and read every line:

	```bash
	git diff 8d9ab41 -- apps/web
	```

	Classify every difference: a functional difference the contract calls for is the build target; a visual difference that would exist even with perfect data is drift and is fixed in this slice; a visual difference reality forced is a delta and is recorded.
