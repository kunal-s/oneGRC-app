## 1 Outcome

A file a person chooses actually reaches the platform: it is scanned, held to a
type and a size limit, stored once under the hash of its own bytes, served back
byte for byte with its integrity rechecked, and a register the server can read
leaves the platform as a real file carrying the caller's own scope on its face.

---

## 2 Functional purpose

Two people meet this slice, at the two ends of one problem. The first is the person
who did the work. Deepa Iyer pays the June profession tax and the platform asks her
for the treasury challan. FRD §5.6 states why the ask exists in a line worth reading
twice: proof should be a byproduct of doing the work rather than a separate act of
documentation, because "done but not documented" is the single most painful real
finding a firm meets. The whole of `BR-EVD-01` rests on the artifact being an
artifact. The second is the person who has to answer for it: an inspector, an
internal auditor, or the Compliance Manager preparing for either, who asks for the
register as it stands and gets a file they can open, read and hand on. FRD §10.4
governs what that file must say about itself, and `BR-DAT-06` governs whose rows it
may carry, with the reason stated in the FRD itself: an export is the easiest way to
defeat an access model.

The FRD grades both Essential. G-13 reads "Export, upload and file handling: mocked
as a preview drawer and a toast", and names what must replace it: real file upload
with virus scanning, type and size limits, storage with retention, and real export
formats. G-14 reads "Evidence storage: evidence items are records without payloads",
and names artifact storage, integrity hashing, retention enforcement and legal hold.
FRD §19.3 lists evidence storage among the six floor items no deployment may
simulate. `platform.md` carries the same two gaps at FLR-05 and FLR-11.

Name the fiction. Nothing in this product has ever held a file a user chose.
`EvidenceDetail.tsx` renders a dashed drop zone whose `Choose file` button sets the
literal string `evidence-upload.pdf` and reads nothing; its `Download` button raises
a toast reading `<id>.pdf` and produces nothing. Every register header carries an
`Export` button that raises a toast naming a filename that was never written:
`source-library-register.csv` on the Source Library, `evidence-vault-index.csv` on
the vault. `useGenerateReport` records a session artifact in a Zustand store and
opens a drawer whose body says the document "is ready to download as a PDF"; the
primary control raises `Action completed.` and closes. Every `Evidence` row in the
database carries a null `documentSha256`, so the vault is a list of claims about
files nobody can open. SIM-NAV-005 records the whole of it in one line: the drawer
previews a filing, an upload or an export, then raises a toast, and no file is
produced, sent or stored.

What survives untouched is the half that is already real. The content-addressed
store exists, holds the four fixture instruments, deduplicates by hash and reverifies
on read. This slice makes it serve its second consumer, which is what ENG-05 always
said it would, and puts nothing beside it.

### FIL, what the platform accepts

| Line | Fact |
|---|---|
| FIL-001 | Every file entering the platform passes one intake. There is no second upload path, no second store and no second hash. `platform.md` ENG-05, ILL-19 |
| FIL-002 | The accepted types and the size ceiling are configuration, seeded as reference data, not constants compiled into a handler. FRD §14.1 makes limits configuration and M-16 gains the editing surface in [[SLICE-43]]. This slice builds no editing surface |
| FIL-003 | The accepted set, recommended under DN-038 and implemented here: PDF, PNG, JPEG, CSV, plain text, `.docx` and `.xlsx`. Each is a form E-31's own `kind` enum actually arrives in: a filing acknowledgement, a challan, a committee minute, a screenshot, a configuration export, a log extract |
| FIL-004 | The ceiling, recommended under DN-038: 25 MB for one file. The largest instrument in `fixtures/` is 2.6 MB and a scanned challan sits well under 10 MB |
| FIL-005 | The type is decided by the bytes, not by the filename extension and not by the `Content-Type` the browser declared. A client can assert anything, and a rule that trusts the client is not a rule |
| FIL-006 | A file above the ceiling, or of a type outside the set, is refused with REF-28: `<type> files up to <size> are accepted.` The rendered message names the accepted set and the ceiling, because a refusal a user cannot act on is a defect. `platform.md` section 6, FRD G-13 |
| FIL-007 | The refusal happens before any byte is written to the store and before any row is created. A refused file leaves nothing behind |
| FIL-008 | A zero byte file is refused on the same message. It proves nothing, and every empty file hashes to the same address |
| FIL-009 | One file per attach. Multiple selection is not offered. DEF-09 defers bulk evidence attachment and this slice does not pre-empt it |

### FIL, scanning

| Line | Fact |
|---|---|
| FIL-010 | Every file is scanned before it is stored. A file that fails is refused, nothing is written and no record is created. FRD G-13 |
| FIL-011 | Scanning sits behind one port with one interface, the way `EnrichmentProvider` does for ENG-11. Two implementations ship |
| FIL-012 | The first calls a locally installed `clamd` daemon, selected by `FILE_SCANNER=clamav` with its socket configured. A local package is the same class of dependency as the poppler-utils the on-premise image already installs for `PdfTextService`, so CON-01 and CON-03 both hold: nothing leaves the deployment and an air-gapped install still works |
| FIL-013 | The second is the default where no scanner is configured. It performs structural checks only: the type check of FIL-005, the size check, the zero byte check, and the EICAR test signature. It is not a malware scanner and it says so, on the health endpoint and in the drawer, reading `Structural checks only. No malware scanner is configured.` Simulating something is acceptable; simulating it quietly is not. `platform.md` section 7 |
| FIL-014 | Where a scanner is configured and cannot be reached, the intake refuses. A scanner that could not be reached is not a scanner that passed. The message names the reason |
| FIL-015 | A refused upload commits nothing and writes no audit entry, consistent with [[SLICE-01D]] CON-007. That a refused upload therefore leaves no trace is raised as ER-016, unbuilt |

### FIL, storage

| Line | Fact |
|---|---|
| FIL-020 | Bytes are stored by the SHA-256 of their content, through the existing `DocumentStoreService`. No second store appears. `platform.md` section 1, ENG-05 |
| FIL-021 | Identical bytes are stored once. `put()` already recognises a blob it holds and returns `written: false`. Two records citing the same artifact are two references to one blob, which is the second reason the store is content addressed |
| FIL-022 | One E-13 `Document` row per stored blob, carrying `sha256`, `byteSize`, `mimeType`, `pageCount`, `storedAt` and `origin`. `data-model.md` E-13. No field is added to E-13 |
| FIL-023 | `origin` on a Document created by an upload is `earned`. Section 5 of `data-model.md` permits `sample` and `earned` on E-13 |
| FIL-024 | The Document row, the record citing it and the audit entry are written in one transaction through `GovernedMutationService.run()`. AUD-01, D-017. The bytes are written to the store first, because a filesystem write cannot join a database transaction. An orphaned blob is harmless; a Document row pointing at bytes that are not there is not |
| FIL-025 | A read rehashes the bytes and compares before returning them, and refuses by name where they differ. `get()` already does this. Silent bit rot in an evidence store surfaces only when a regulator asks, which is the worst possible moment to find it |
| FIL-026 | `pageCount` is read from the file for a PDF, is null for every other type, and is null where it cannot be read. It is a property of the bytes rather than a derivation over other fields, so storing it is not a breach of rule 1 |
