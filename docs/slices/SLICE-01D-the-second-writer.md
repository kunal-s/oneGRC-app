## 1 Outcome

Two people acting on the same record at the same time no longer overwrite each
other silently: the second writer is refused, told who changed what and when, and
sent back to look before trying again.

---

## 2 Functional purpose

This slice has no screen a user goes to. It exists for the moment a user does not
expect: two people working the same record within the same minute.

FRD §17.5 states the requirement in one line. Two people acting on the same
record must not silently overwrite one another, and the later actor is told what
changed. FRD §19 G-04 grades it Essential and names the prototype's position:
single user, single session, no concurrency. FRD §23 D-20 records the demo
shortcut and the correction: optimistic versioning with a visible conflict path,
the second writer told what changed, never silently overwritten. `platform.md`
FLR-07 carries the same gap on the floor, reading "Not real. Single user, single
session."

The reason it matters in this product specifically is the audit trail. Every
governed mutation already writes exactly one hash-chained audit entry naming the
actor, the action, the object and the before and after values, and a change that
cannot be logged does not commit. That machinery is built. What it cannot do is
notice that the before value it recorded was already stale when the caller read
it. Anjali opens an obligation cycle, reads its due date, and steps away. Vikram
amends the same cycle. Anjali returns and approves. The log now holds two truthful
entries and one of them describes a decision taken against a record that no longer
said what Anjali thought it said. The trail is intact and the decision behind it
is not. `BR-AUD-01` gives an auditor the history; only this slice gives them the
assurance that each entry was written by somebody looking at the current record.

The refusal is already specified. REF-25 in `platform.md` section 6 reads
`<person> changed this record at <time>: <what changed>. Review and try again.`
It names the person, the time and the change, because a refusal a user cannot act
on is a defect.

## 3 Screen contract

This slice has no region of its own. Its contract is a rule applied to every
governed write, plus the one surface that renders the refusal.

Behaviour and rules from `docs/plan/` and the FRD per D-042. There is no
prototype behaviour to reconcile against, because the prototype has none: FRD §23
D-20 records that a one-presenter demo needed no concurrency.

### The versioning rule

| Line | Fact |
|---|---|
| CON-001 | Every entity carrying a governed transition carries a version marker that changes on every governed write to it. FRD §17.5, D-20 |
| CON-002 | The version marker is not a derived value and does not violate rule 1. It records a fact about the row's write history that nothing else in the record implies |
| CON-003 | A read that a write will later be based on returns the version marker it read at. `platform.md` section 2, the seam |
| CON-004 | A governed write carries the version marker the caller read. A write that does not carry one is refused, so a client that has not been updated cannot bypass the check by omission |
| CON-005 | The check runs inside `GovernedMutationService.run()`, in the same transaction as the work and the audit entry, so a conflict is detected against the row as it stands at commit rather than as it stood at read. `platform.md` section 5 |
| CON-006 | The check runs after the authority check and before the work. A caller who may not perform the action at all is refused for that reason, not for a conflict |
| CON-007 | Where the version marker differs, the write is refused and nothing is committed. No partial write, no audit entry for an action that did not happen. `platform.md` AUD-01 |

### The refusal

| Line | Fact |
|---|---|
| CON-010 | The message is REF-25, exactly: `<person> changed this record at <time>: <what changed>. Review and try again.` `platform.md` section 6 |
| CON-011 | `<person>` is the full name of the person who made the intervening change, resolved from the audit entry that recorded it. It is never an identifier and never blank |
| CON-012 | `<time>` is rendered in the organisation's time zone. FRD §17.7. **The one clock service ENG-09 is not built**, so this slice reads the time directly and records the dependency. See section 8 |
| CON-013 | `<what changed>` names the fields the intervening change touched, taken from the before and after values already held on the audit entry. It is not a generic phrase |
| CON-014 | For a confidential module the refusal names the act and never the content. `platform.md` AUD-06, `BR-AUD-05`. A conflict on a speak-up or fraud record says a change happened and by whom, and nothing about what |
| CON-015 | The refusal is shown where the user was acting, and the form they filled is not cleared. Losing the second writer's work to tell them about the first writer's is the failure this slice exists to prevent |
| CON-020 | Visual treatment: reuse the refusal presentation [[SLICE-01C]] establishes for REF-01 to REF-05. This slice adds no new visual vocabulary. `NOT SPECIFIED` beyond that, because the prototype has no refusal surface for D-042 to rule on |

### What does not change

| Line | Fact |
|---|---|
| CON-030 | A read is never refused for a conflict. Only a write |
| CON-031 | Two writes to different records never conflict, however close in time |
| CON-032 | A second write by the same person, having read the record again, succeeds. The rule is about staleness, not about who is writing |
| CON-033 | Nothing about separation of duties changes. A maker still may not approve their own work, and that refusal fires before this one. `BR-AUT-05`, SCR-088-073 in [[SLICE-01C]] |
| CON-034 | The audit chain is unchanged. No new entry kind, no change to the hash, and `pnpm --filter api verify:audit` continues to pass |

## 6 Out of scope

- **Sign-in, the session, the view selector, the department boundary, the authority gates.** [[SLICE-01A]], [[SLICE-01B]], [[SLICE-01C]].
- **The one clock service ENG-09.** [[SLICE-05]] builds it. This slice reads the time directly and records the dependency rather than building a second clock.
- **Live collaboration of any kind**: presence indicators, showing who else has the record open, real-time updates, locking. FRD §17.5 asks for optimistic versioning with a visible conflict path and nothing more. Anything else is an enhancement and is unapproved.
- **Merging two writers' changes.** The second writer reviews and tries again. FRD §23 D-20 says told, not merged.
- **The full refusal catalogue ENG-15.** [[SLICE-05]].
- **Improving, tidying or refactoring anything passed through.**

## 7 Verification

This is the one slice in the group whose verification needs two people at two
machines, or one person in two browsers signed in as two people.

1. Confirm the prototype has no conflict path at all: two browsers, same record, both save, and the second silently wins. This is the behaviour the slice removes.
2. In the build, sign in as Anjali in one browser and Vikram in another, on the same record.
3. As Anjali, open the record and begin an amendment. Do not save.
4. As Vikram, amend the same record and save. Confirm it succeeds.
5. As Anjali, save. Confirm the write is refused.
6. Read the refusal. Confirm it names Vikram by his full name, gives the time of his change in the organisation's time zone, and names what he changed. Confirm it is not a generic phrase.
7. Confirm Anjali's form still holds what she typed. Nothing she entered may be lost to the refusal.
8. Reload as Anjali, make the same amendment against the current record, and save. Confirm it now succeeds.
9. Ask the administrator to show the audit log. Confirm there is exactly one entry for Vikram's change and one for Anjali's successful second attempt, and no entry at all for her refused first attempt.
10. Repeat steps 2 to 6 on two different records, one each. Confirm neither conflicts with the other.
11. Repeat as one person: Anjali in two browsers. Confirm she is refused in the second, on the same terms. The rule is about staleness, not about who.
12. On a speak-up or fraud record, repeat steps 2 to 6. Confirm the refusal names the act and the person and says nothing about the content of the change.
13. Confirm a maker still cannot approve their own work, and that this refusal fires before the conflict refusal when both apply.
14. Run `pnpm --filter api verify:audit`. Confirm the chain still walks clean.
15. Run the verification commands. All pass.
16. Run the UI drift check and read every line:

	```bash
	git diff 8d9ab41 -- apps/web
	```

	Classify every difference. A new refusal appearing is the build target under FRD §17.5. Any change to a screen's appearance outside the refusal is drift.
