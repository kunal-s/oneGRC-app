## 1. Stack

Chosen and in place before this plan was written. Recorded here because the plan
builds against it, not because it is open.

| Layer | What | Why |
|---|---|---|
| Repository | pnpm workspace: `apps/web`, `apps/api`, `packages/domain` | One repository holds the approved frontend, the new backend, and the types the seam speaks |
| Frontend | React 18, TypeScript, Vite, Tailwind, React Router, Zustand, TanStack Query | Inherited from the prototype unchanged. Query is added for the wired screens, so a register can move to server-side paging without touching the components |
| Backend | NestJS on Fastify, TypeScript | Modules map one to one onto the modules in this plan, and dependency injection is what lets one authority check and one audit writer sit in front of every handler |
| Database | PostgreSQL 16, via Prisma | Relational, because the whole product is a connected model, and because the audit chain needs transactional writes alongside every mutation |
| Document store | Content-addressed files on disk, addressed by SHA-256 | An extracted clause must be provable against the exact bytes it came from. A hash is that proof, and it also deduplicates |
| Local runtime | Docker Compose, one Postgres service | One command to a working database, on any machine |
| Identity | Server-side sessions today, federated to the customer identity provider later | The client never asserts who is acting |

**Constraints stated by the FRD, carried as constraints.**

| ID | Constraint | Source |
|---|---|---|
| CON-01 | On-premise or private deployment must be possible, because the law may require personal and regulatory data to stay within a jurisdiction | FRD §15, `BR-DAT-04` |
| CON-02 | The control plane and the data plane must be separable, so a customer can adopt the model without moving their systems of record | FRD §2 |
| CON-03 | No dependency on a third-party service that would make an air-gapped deployment impossible | FRD §15 |
| CON-04 | Vendor neutral. The product integrates with whatever the customer runs and is never architecturally bound to one vendor | FRD §12.2 |
| CON-05 | Evidence and the audit log are append-only and are never pruned below their retention floor | FRD §17.1, `BR-DAT-05` |
| CON-06 | The audit log must be tamper-evident: hash-chained, written in the same transaction as the change it records | FRD `BR-AUD-02` |
| CON-07 | Registers must page and filter server side at full customer volume | FRD §17.2 |
| CON-08 | Derived values must never be stored, and any materialisation for cockpit performance must invalidate on the writes that affect it | FRD §17.2 |
| CON-09 | Where a model is introduced behind the intelligence seam, customer data may not be used for training, and that must be contractual | FRD §13.4 |

## 2. The seam

One doorway between the screens and the data. One function per read and per
write, named after what it does, asynchronous from day one even where the answer
is instant. This is what lets a slice swap a screen from the seed world to the
database without touching the components around it.

**Where it lives.** `apps/web/src/api/client.ts` is the transport.
`apps/web/src/api/types.ts` and `packages/domain` hold the types both sides
speak. A screen calls a named function; it never builds a URL and it never
reaches into the store for something the server owns.

**The rule that makes it work.** A screen may read from exactly one of two
places: the seam, or the seed world. Never both, and never in the same
component. `apps/web/src/pages/ControlDetail.tsx` currently breaks this by
falling back from the seed to the API inside one component, which is why SCR-021
closes out with M-04 rather than being left as it is.

**Writes do not appear in section 3.** Every write lives in
`docs/plan/workflows/` against the transition it performs, so an action and its
consequence stay one fact.

Two rules apply to every read. **Discovery is scoped**: a register, a calendar
and the queue return only records owned within the caller's department, except
for Compliance and Company Secretarial and the Administrator, who see all.

command search, so a cross-reference never dead-ends. The exception is R-051,
where a stronger rule applies and the body is refused outright.

## 4. Authorisation

**One central check, and no screen performs its own role comparison.** Every
governed action resolves through `AuthorityService.assert()`, which reads the
matrix from the `ActionAuthority` table. That table is data, maintained through
the governed configuration workflow, so a customer can tighten an approver set
without a code release and there is exactly one table to review.

**The rule stated plainly.** Hiding a button is presentation. Refusing the call
is the control. The client renders capabilities the server computed (R-002); it
never decides them.

The check runs three gates in this order, and it is already built this way:

| Gate | What it does | FRD rule |
|---|---|---|
| Role | The action must have at least one permitted role that the caller holds. An action with no rows at all is refused, so a typo in an action name cannot become an unguarded endpoint | `BR-AUT-01`, `BR-AUT-03` |
| Department | Evaluated per row (AUTH-G3, D-046, [[SLICE-01C]]): the caller is permitted when at least one row they hold is satisfied completely, meaning it names no department or names theirs. This is how clause authority belongs to Compliance and Company Secretarial rather than to the Compliance Manager role, and how `instrument.create`'s two non-uniform rows (D-037) both work correctly for the same caller | `BR-AUT-02` |
| Separation of duties | Where a permitted row carries the separation flag and a maker is named, the caller may not be that maker | `BR-AUT-05`, `BR-AUT-06` |

**Two gates the check does not yet run correctly, and one now closed.**

| ID | Missing gate | What it must do | FRD rule | Slice |
|---|---|---|---|---|
| AUTH-G1 | Line of defence | Half closed. `ActionAuthority` carries `requiresLineOfDefence` and the check reads it, but the column is empty for every action, so nothing is barred yet ([[SLICE-01C]], D-047). Where the customer configures it, the checker must sit in a different line from the maker, and the owner of a control may not raise the working paper that tests it | `BR-AUT-10`, §21.12 | which actions get it, a later decision |
| AUTH-G2 | Case access and recusal | For every speak-up and fraud action, role membership is necessary and never sufficient. The case-level rule decides, and it overrides the matrix | `BR-SCP-05`, `BR-SCP-06` | [[SLICE-26]] |
| AUTH-G3 | Per-row evaluation of the department gate | Closed by [[SLICE-01C]], D-046, DN-023. The gate now asks whether at least one held row is satisfied completely, rather than whether every held row names a department, so one ungated row can no longer switch the department test off for a gated row held by the same caller. `instrument.create`'s two non-uniform rows (D-037) are the proof: Priya Sharma, who holds Compliance Manager outside Compliance and Company Secretarial, is refused; Anjali and the Administrator are both permitted, from the same table | `BR-AUT-02` | closed |

## 5. Audit

**Append only, hash chained, transactional with the change it records.** Every
mutation writes exactly one entry naming the actor, the action, the object, the
timestamp and, where relevant, the before and after values. A change that cannot
be logged does not commit. This is built: `GovernedMutationService.run()` runs
the authority check, then opens one transaction that performs the work and
appends the entry, and handlers never write directly.

| ID | Rule | State today |
|---|---|---|

## 6. Refusals

read the same everywhere. The message names the rule, because a refusal a user
cannot act on is a defect.

|---|---|---|---|
| REF-01 | The action name has no authority rows | `No authority is defined for "<action>".` | `BR-AUT-01` |

| REF-03 | The action is department gated and the caller is elsewhere | `<action> is reserved to the <department> department; you are in <department>.` | `BR-AUT-02` |
| REF-04 | The caller is the person who submitted the item | `<action> enforces separation of duties: you submitted this, so you cannot approve it.` | `BR-AUT-05` |
